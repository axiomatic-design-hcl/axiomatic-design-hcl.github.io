Axiomatic Design for software

Write the design once. Let the tool find the coupling.

RequirementsHCL is a language for .ad.hcl files. You write what the software must do, how the design does it, and how the parts affect each other. The adhcl tool derives the design matrices and reports each error and gap.

The language

A typed model of your software

An .ad.hcl file gives people and AI tools one model of the software. The model holds the needs, the requirements, the design choices, and the effects between them.

You write the facts

  • Needs, constraints, assumptions, and contexts.
  • Functional requirements (FRs) with acceptance criteria.
  • Design parameters (DPs) and the decision state of each one.
  • Influences between DPs and FRs, each with a reason.
  • Modules, process variables (PVs), flows, and scenarios.
  • expect blocks that test the result.

The tool derives the results

  • A design matrix for each group of sibling FRs and DPs.
  • A master matrix over all leaf FRs and DPs.
  • The classification: uncoupled, decoupled, or coupled.
  • The design order in which to fix the DPs.
  • Missing criteria, modules, and scenarios.
  • Each claim that has no reviewed support.
Core ideas

Four ideas carry the whole language

fr

An FR states an outcome

A functional requirement says what the software must give, for example "Save a new note." An acceptance criterion says when it succeeds, for example "within 200 ms".

dp

A DP controls an outcome

A design parameter is the part of the design that controls an FR, for example "a table with one row for each note". A process variable (PV) is the code or resource that makes the DP real.

influence

Unknown is not zero

Each influence says that a DP has a material effect on an FR, no effect, or an unknown effect. A cell that nobody wrote is unknown. The tool never guesses a zero.

support_gap

A claim is not a proof

An effect that you write is a claim. A valid model does not prove that the design is independent or that code exists. The report says which claims have no reviewed support.

The design matrix

Three kinds of design

The matrix has one row for each FR and one column for each DP. X is a material effect, 0 is no effect with a reason, and ? is unknown. The Independence Axiom says: “Maintain the independence of the functional requirements.” In the papers, a cell is a number: the rate of change of the FR when the DP changes. RequirementsHCL uses symbols, because many effects in software are not numbers.

Uncoupled
DP1DP2
FR1X0
FR20X

Each DP changes only its own FR. You can set the DPs in any order.

Decoupled
DP1DP2
FR1X0
FR2XX

In a suitable order, the effects form a triangle. The FRs stay independent only if you set DP1 first, then DP2.

Coupled
DP1DP2
FR1XX
FR2XX

No order gives a diagonal or a triangle. A change to one DP forces changes to the other. This design does not satisfy the Independence Axiom.

If one cell is ?, the tool reports the classification as unresolved. You must state every cell, one by one or with a default.

An example

A notes app in one file

The app saves notes and finds them by a word. The index reads the stored rows, but the save replies before the index updates.

fr "save_note" {
  need      = [need.keep_ideas]
  statement = "Save a new note."
  criterion "save_time" {
    metric = "milliseconds to the reply"
    op     = "<="
    value  = 200
    unit   = "ms"
  }
}

dp "note_store" {
  controls       = [fr.save_note]
  responsibility = "Write each note as one row."
  decision       = "selected"
}

influence {
  from      = [dp.note_store]
  to        = fr.find_notes
  effect    = "material"
  mechanism = "The index reads the stored rows."
}

influence {
  from    = [dp.word_index]
  to      = fr.save_note
  effect  = "none"
  because = "The index updates after the reply."
}

  Pairing: fr.find_notes with dp.word_index,

The design is decoupled. Decide note_store first, because it affects both FRs. If you change the row format later, you must test find_notes again.

Rules

The rules of the language

The language is native HCL, the syntax that Terraform uses. The rules are stricter than Terraform, so that a model means one thing only.

  1. Write each fact once. Never write a matrix, an ID number, or a classification by hand.
  2. An influence with effect = "material" needs a mechanism. An influence with effect = "none" needs a because.
  3. Mark your own reasoning with origin = "inferred" or mechanism_source = "inferred".
  4. Do not invent targets, mechanisms, or probabilities. Leave the gap, and let the tool report it.
  1. A reference is fr.save_note, not the string "fr.save_note".
  2. Labels use snake_case. Keep source IDs such as FR11 in alias.
  3. No arithmetic, functions, conditions, or templates. Each value is a literal.
  4. Unknown blocks, unknown fields, and null are errors. The tool ignores nothing.
Files

Three kinds of file

Core files hold the design facts. Data for other tools goes into attachments, so it cannot change a core fact.

SuffixContentsLoaded when
.ad.hclCore facts: the design root, needs, FRs, DPs, influences, decisions, modules, and scenarios.You give one file, or a folder. A folder merges its direct *.ad.hcl files.
.ad.ext.hclAttachments: a Terraform binding on a PV, a link to a behavior model on a module, or a view on the design.Only when a manifest lists the file.
.ad.project.hclThe manifest: the list of core files, attachment files, and extension owners.You give the manifest path.

Split a large model by domain and by branch. Never put the FRs in one file and the DPs in another file. Put each influence that crosses branches in the file of the nearest common parent.

The tool

adhcl reads the model and writes a report

adhcl is a command line tool in Go. It parses the input, resolves the references, runs the core assessment, and prints a text report. It reads files only. It does not run your code or connect to a network.

Install

You need Go 1.25 or later.

  1. Clone the repository: git clone https://github.com/axiomatic-design-hcl/adhcl.git
  2. Go into the folder and run make build. The binary goes to bin/adhcl.
  3. Run bin/adhcl version. A local build prints adhcl dev.

Commands

adhcl version
adhcl validate [--profile source|architecture]
               [--candidate REF] [--context REF]
               [--] PATH
adhcl --help

PATH is one .ad.hcl file, a folder, or a .ad.project.hcl manifest. Put the options before the path.

Profiles

Two levels of strictness

A profile changes the severity of some findings. It does not change the claims in the model.

ProfileUse it for
sourceThe default. Early designs and models of a paper. Gaps such as a missing criterion, module, or scenario are warnings.
architectureA design that is ready to build. The same gaps are errors.

These codes are warnings under source and errors under architecture: incomplete_criterion, incomplete_module_contract, missing_leaf_scenario, incomplete_feedback_contract, unresolved_refinement, unresolved_applicability, unresolved_influence, and shared_resource_review_gap.

Exit codes

What the result means

CodeMeaning
0Validation completed with no error findings.
1An input, parse, assessment, attachment, or output step failed.
2The command line is wrong.

Exit code 0 does not prove that the design is independent, that it is built, or that observations support it.

The report

Five parts, always in the same order

  1. The header: input, tool version, contract, profile, candidate, context, and workload.
  2. Findings: each error and warning, with its code, subject, file, line, and message.
  3. Scopes: the classification, pairing, design order, and cycles of each matrix.
  4. Owners: the result of each attachment.
  5. Summary: the counts, the status of each stage, and the open causes.
Findings
- error invalid_reference on dp.wordindex
  at notes.ad.hcl:67:11: dp.wordindex does not
  name a declared block. This field needs a dp.
- warning support_gap on notes.ad.hcl:45-50:
  The claimed influence from dp.note_store

Each code is stable. The diagnostic contract lists all codes and their severity in each profile.

Claude Code plugin

Let Claude make the design and write the files

The Axiomatic Design plugin adds two skills to Claude Code. A skill is a set of instructions and reference files that Claude loads for one kind of task.

axiomatic-software-design

Apply the method

Claude maps needs to FRs and DPs, builds the matrices, finds coupling, and compares alternatives on evidence. The result is an architecture with module contracts.

adhcl

Write the .ad.hcl files

Claude turns a finished design into .ad.hcl files without changes to its facts. Then it runs adhcl when the tool is available.
